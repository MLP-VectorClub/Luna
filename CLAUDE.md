# Luna

Laravel API for the MLP Vector Club. Deployed by pushing `main` to the `deploy` remote (git-deploy-toolkit, see `deploy.conf`); `origin` is GitHub.

## Stack

Laravel 13 on PHP 8.5 (`composer.json` requires `^8.5`, `webpatser/laravel-uuid` 7 needs it), PHPUnit 13. `citext` / `mlp_generation`-style column types are grammar macros in `AppServiceProvider` (no DBAL). Search runs on OpenSearch through `opensearch-project/opensearch-php` (array requests and responses; `config/opensearch.php` + `App\Utils\Search` build the client and classify failures: `Search::status`, `errorBody`, `isDown`), queries in `ColorGuideHelper` are plain arrays; the index `appearances` is rebuilt by `AppearanceIndex`. The API is documented with swagger-php PHP attributes (`#[OA\Get(...)]`, `#[OA\Schema(...)]` with nested `new OA\Property(...)`, constants such as `\DATABASE_ROLES` come from `config/l5-swagger.php`), scanned by l5-swagger 11 (swagger-php 6); there is no `doctrine/annotations` and docblock `@OA` annotations would be ignored. The OpenAPI JSON is pinned to `/generated/api-docs.json` (l5-swagger serves it at the route itself).

Not covered by tests: `AccountHelper::create` (first user becomes developer), search/autocomplete against a real server, social signin against the real providers. `StrictEmail` is `email:rfc,dns`; its DNS part needs network.

## API contract

Luna implements the `/api/v0` contract that Winterchilla's front end used (`docs/contract/api.json` is a frozen copy; Celestia builds its types from Luna's own generated document, see below).

### Built (all 130 operations of the contract)
- Schema alignment migration `2026_10_01_000000_align_schema_with_winterchilla` (drops `show_videos` and `show.generation`, restores `UNIQUE(season, episode)`, discriminator smallint, FK and timestamp fixes, dead rows)
- Foundation: `GET /config`, `role:` and `optional.auth` middleware, `{message}` error bodies (`ConflictException` adds extra fields to a 409), `POST /test/login/{id}` (APP_ENV=testing only), `/users/me` as `{user, sessionUpdating}`
- Settings, notices, useful links, user preferences (+ `PUT /users/{id}/role`), tags, color groups, appearances (reads and all management except cutie marks), sprites, shows (incl. votes, next, latest, prefill), admin logs, notification read, color guide export and reindex, personal guide (slots, points, history), post lists, post write flows (create, edit, reserve, finish, approve, delete, change image, unbreak, direct reservations), user profile and contributions, event reads, the disabled event writes (501 like Winterchilla), cutie marks (`App\Http\Controllers\CutieMarksController`, stored as medialibrary files holding the sanitized SVG) and SVG sanitizing (`App\Utils\SvgHelper`, enshrined/svg-sanitize, minified by the sanitizer, no svgo), Discord sync and unlink (`DiscordController`, Laravel `Http` against discord.com, needs `DISCORD_CLIENT_ID/SECRET/BOT_TOKEN/SERVER_ID`)
- Image links go through `App\Utils\ImageProvider` and `DeviantArt` (oEmbed, Derpibooru, Imgur, Lightshot, club gallery check), always via Laravel's `Http` client so tests fake them
- `App\Utils\AppearanceIndex` keeps the shared OpenSearch `appearances` index in sync; `LogWriter` writes the shared `logs` table

### Cutie mark colors follow the guide
Like Winterchilla's tokenized files: `CutieMark::storeSvg` replaces every color of the sanitized SVG that the appearance's `Cutie Mark` color group has by a token (`SvgHelper::tokenize`, `<!--@ID:RRGGBB[,ALPHA]-->`, unknown colors `<!--#/RRGGBBAA-->`) kept in the media's `tokenized` custom property, and serves the file with the current colors. Saving that color group (`ColorGroupsController`) calls `CutieMark::rerenderAllOf`, which writes a new file (new hash name, so the URL changes and nothing stale is cached). The token carries its own hex, so a deleted color keeps rendering. Marks stored without tokens (no color group at the time, or imported from Winterchilla) stay as they are until `php artisan cutiemarks:tokenize` (`--dry-run` to preview; safe to repeat, it skips marks that have tokens). Colors changed by other routes than the color group save (deleting the group contents, templates) do not re-render, the files keep their last colors. Tests: `SvgTokensTest`, `CutieMarksTest`.

### Data for the episode page (not in Winterchilla's contract, which renders this as HTML)
`GET /posts/{id}/deviation` (the DeviantArt submission of a finished post: title, author, images from the cached oEmbed data, 404 when unknown or unfinished, 502 when DeviantArt fails; Celestia loads it as a post scrolls into view), `GET /show/reservation-info` (the two admin-edited, already sanitized texts "What Vector Reservations Are" and "Reservation Rules", public) and `GET /show/{id}/adjacent` (previous and next entry for the heading buttons, by overall number for episodes). Tests: `PostDeviationTest`, `ShowEpisodePageDataTest`.

### Left
- Cutie mark gaps: no svgo (deliberate: the sanitizer minifies), attribution by username/deviation needs the DeviantArt user to exist already (no DeviantArt API lookup to create unknown users), the `preview` HTML of Winterchilla is not returned
- Event entries: `GET|PUT|DELETE /event-entries/{entryid}` are implemented (`EventEntriesController`, PUT answers `{}` without Winterchilla's `entryHtml` UI field); `GET|PUT|DELETE /events/{id}/entries` are placeholders that answer 404 for signed in users like Winterchilla (its route never gets an entry id)
- Not in the contract: `GET /appearances/{id}/preview` (internal); no test talks to a real OpenSearch server

### Self-contained without Winterchilla
Luna keeps copies of what it needs from Winterchilla so the repo works if Winterchilla is deleted: the contract (`docs/contract/api.json`), the contract seed and cutie mark fixture (`tests/fixtures`), the image goldens and the fonts/graphics. Only the `scripts/generate-winterchilla-*-goldens.php` regenerators and Winterchilla's own Pest contract tests need the Winterchilla repo.

### Account changes (x-internal in Winterchilla; own account for everybody, other users' addresses for developers)
`POST /users/me/password` (`UsersController::setPassword`, deletes all of the user's tokens), `POST /users/{id}/email-changes` (any signed in user for their own account, developers for other users') and `POST /users/email/verify` (any signed in user, `verify` only for their own verification (403 otherwise), `block` needs just the hash; `UserEmailController`, mail `App\Mail\VerifyEmailAddress` with views in `resources/views/emails`). The verification link points to `FRONTEND_URL/users/verify?hash=<128 hex>&action=verify|block` (Winterchilla's page path, Celestia needs a page that posts both values to `POST /users/email/verify`). Sending needs working `MAIL_*` settings in `.env`. `config/mail.php` accepts `MAIL_FROM` as an alias of `MAIL_FROM_ADDRESS`, the sender name defaults to "Penny Curve"; port 465 needs `MAIL_SCHEME=smtps`. Production sends through the mail server on the same machine (`MAIL_HOST=localhost`, `MAIL_PORT=25`, no username or password, `MAIL_FROM=noreply@mlpvector.club`), set `MAIL_AUTO_TLS=false` there: the local server answers `454 4.7.0 TLS not available due to local problem` to STARTTLS and accepts the message once `auto_tls` is off (`MAIL_VERIFY_PEER=false` is for certificate problems). Check the settings with `php artisan mail:test <address>` (prints the mailer and either success or the transport error).Delivery failures answer 503 and remove the verification. `StrictEmail` can skip its DNS lookup with `config('app.email_dns_check')` (tests). Forgotten passwords have their own flow, see the next sections.

### E-mail addresses are encrypted
`users.email` holds the address encrypted with the app key (`App\Utils\EmailVault`, Laravel's encrypter: a different ciphertext every time) and `users.email_hash` a keyed hash (HMAC-SHA256 of the lowercase, trimmed address; the key is `EMAIL_HASH_KEY`, else `APP_KEY`) with a unique partial index, which is what lookups and uniqueness go by. `User`'s `email` attribute reads and writes plain addresses (assigning one sets both columns), `User::whereEmail($address)` finds by address whatever its case, `App\Rules\UniqueEmail` replaces `unique:users` for it, `email_hash` is hidden. Never `where('email', ...)`: the column holds ciphertext. The migration `2026_10_16_000000_encrypt_user_emails` encrypts what is there (production had 1 address in 1501 users); `php artisan users:encrypt-emails [--dry-run] [--rehash]` does the same for plain addresses that somebody else wrote, reports accounts that share an address apart from its case (the first keeps the index, the other is not findable by address) and, with `--rehash`, encrypts everything again and rebuilds the hashes (after an `APP_KEY` change: put the old key in `APP_PREVIOUS_KEYS` first, set `EMAIL_HASH_KEY` beforehand to keep the hashes). A value that does not decrypt reads as no address, never as the ciphertext. Not encrypted: `email_verifications.email` (kept 24 hours) and `blocked_emails.email` (the do-not-send list of addresses that are not necessarily users). Tests: `EmailEncryptionTest`.

### Two-factor authentication and passkeys
Tables of Luna's own (`users` is shared with Winterchilla): `luna_two_factor` (TOTP secret encrypted with the app key, `confirmed_at`, `last_used_step` so a code works once), `luna_recovery_codes` (HMAC of the code, ten per setup, shown once) and `luna_passkeys` (credential id plus the serialized `Webauthn\CredentialRecord`). `POST /users/signin` answers **202** `{twoFactor: {challenge, methods}}` when the password is right and the account has a confirmed authenticator app: nobody is signed in yet (not a 401, which Celestia shows as wrong credentials). The `challenge` is an encrypted, expiring (5 minutes), single use token (`App\Utils\SignedChallenge`, no session, so bearer clients and guests work the same and nothing is left behind); `POST /users/signin/two-factor` takes it with `code` or `recoveryCode` (5 tries per challenge, 10 wrong answers per account per 15 minutes, then 429) and ends in `AccountHelper::authResponse` like any other sign-in. A passkey also answers it (`signin/two-factor/passkey/options` + `signin/two-factor/passkey`). `POST /users/signin/passkey/options` + `/users/signin/passkey` sign in with a passkey alone (discoverable credentials, empty `allowCredentials`; the options token lives ten minutes because browsers keep the autofill request open while the visitor types). OAuth sign-ins (DeviantArt, Discord) are exempt on purpose. Managing (`users/me/two-factor*`, `users/me/passkeys*`) asks for `currentPassword` again (`App\Utils\IdentityCheck`, a code of the app for accounts without a password) and ends the user's other sessions and tokens when a factor is confirmed, turned off or removed. The relying party is `config/webauthn.php` (`WEBAUTHN_RP_ID`, default the host of `FRONTEND_URL`, `WEBAUTHN_ORIGINS`): changing it makes every saved passkey useless. A password reset does not turn two-step verification off (reading the mailbox is all it proves), so lost codes and a lost device need a staff fix in the database. Tests: `TwoFactorTest`, `PasskeyTest` (`tests/Support/FakeAuthenticator` makes the browser's answers).

### Forgotten passwords
`POST /users/password/forgot {email}` always answers 202 with the same text (no way to tell members from strangers) and, for an address of an account that is not on the do-not-send list, mails a link (`App\Mail\ResetPassword`, `FRONTEND_URL/users/reset-password?token=<64 hex>`). The mail is sent after the response (`defer()`, which needs `InvokeDeferredCallbacks` in `App\Http\Kernel`'s global middleware: the old-style kernel does not have it by default, so any `defer()` call is a no-op without it), at most `PasswordReset::MAILS_PER_HOUR` (3) per address and hour, counting unknown addresses too. `luna_password_resets` keeps one row per user with only the sha256 of the token, valid 60 minutes, a new request replaces the old link. `POST /users/password/reset {token, newPassword}` (min 8, not pwned) sets the password, deletes the link and every session and token of the account, and works for accounts without a password too. It leaves two-step verification as it is. Tests: `PasswordResetTest`.

### Accounts are made through DeviantArt only
There is no password signup (`POST /users` and `/users/oauth/signup/{provider}` are gone). `POST /users/oauth/signin/deviantart` makes the account when the DeviantArt user has none yet (`AccountHelper::socialDeviantart`: named after the DeviantArt name, role user, no password and no e-mail address; a name an account holds already answers 409, staff has to sort that out), so "sign up" is the same flow as signing in, with the same single redirect address (`FRONTEND_URL/oauth/deviantart`, the provider knows only one). Discord signs in to existing accounts only (linked in the account settings or bound by Winterchilla), unknown Discord users get 404. Members can add a password afterwards through the account page or the forgot-password mail, and passkeys or an authenticator app. Tests: `DeviantArtSigninTest`, `DiscordSigninTest`.

### DeviantArt / Discord sign-in
`AccountHelper::socialDeviantart` follows Winterchilla's login: signing in updates the DeviantArt record, renames the user when the DeviantArt name changed (unless another account already holds the new name) and records the previous names (account name and linked DeviantArt name) in `previous_usernames`, which the profile exposes as `previousUsernames`. New DeviantArt and Discord accounts now get their `user_id` on the linked record (it was missing, so registering through them failed on the NOT NULL column). The DeviantArt Socialite driver forces PKCE (DeviantArt requires it for new apps, Winterchilla enabled it in `8fba523c`, do not switch it off), and Socialite keeps the verifier in the request's session, which a popup opened by the front end may not have (it used to answer 500 "Session store not set on request"). `AccountHelper::socialRedirect`/`socialAuth` now give the request a throwaway in-memory session and carry the verifier in an encrypted, HttpOnly, 10 minute `oauth_pkce` cookie set by the redirect and read by the code exchange (`tests/Feature/DeviantArtPkceTest.php`, Socialite's own Guzzle client is mocked there, not `Http::fake`). Not tried against the real DeviantArt. Sign-in through a popup must report back to the opener window (Winterchilla uses a `BroadcastChannel`, see its `login_confirm.html.twig`), Celestia's `/oauth/[provider]` page only invalidates `users/me` inside the popup.

### DeviantArt token sync (`DEVIANTART_TOKEN_SYNC`, off by default)
Winterchilla's session was a DeviantArt session: every request refreshed an expired token and a failed refresh deleted the session. Luna's e-mail sign-in never touches DeviantArt, so a member who signed in by e-mail keeps access with a dead token. `App\Utils\DeviantArtTokens` refreshes tokens on demand (sign-in and `GET /users/me`); `php artisan deviantart:refresh-tokens` (`--days=7` refreshes records not refreshed for that long, `--force` ignores the switch) does it in bulk but is deliberately not scheduled, so tokens of members who stay away simply expire; when DeviantArt refuses one (HTTP 4xx, or no refresh token) `signOut` clears the tokens of the `deviantart_users` row and deletes all of the user's Sanctum tokens and browser sessions, so only a DeviantArt sign-in brings them back. `GET /users/me` renews an expired access token on the spot (a cache lock keeps parallel requests from using the single-use refresh token twice) and answers 401 `{message, deviantArtRequired: true}` after ending the session; Celestia shows the old site's "Session refresh issue" dialog for that and dims the sidebar user card with the spinner while the refresh takes more than half a second. Outages (5xx, 429, no connection) change nothing. `POST /users/signin` does the same check first for users that have a DeviantArt link: refreshes an expired access token, answers 403 `{message, deviantArtRequired: true}` when it is dead and 503 when DeviantArt cannot be reached; users without a link sign in as before. Everything is behind `DEVIANTART_TOKEN_SYNC=true` (`config('services.deviantart.token_sync')`). A refresh token works only once, which is why it stayed off while Winterchilla served the same accounts; Winterchilla is read-only now and no longer refreshes. Tests: `DeviantArtTokenSyncTest`.

### Client address and rate limits
Production nginx (`/etc/nginx/sites-available/next.mlpvector.club`) proxies the front end's `/api/` to the API vhost on localhost and sets `X-Forwarded-For` to the visitor's address (it resolves Cloudflare's `CF-Connecting-IP` first); on the API vhost that request arrives from 127.0.0.1. Luna trusts Cloudflare's ranges (Monicahq `TrustProxies`) and now also `127.0.0.1`/`::1` (`AppServiceProvider::boot`), otherwise every browser of the front end shared one rate limit bucket. Limits: reads (GET/HEAD) 1200 per minute and client, everything else 60 (`THROTTLE_READS`, `THROTTLE_WRITES`, named limiter `api`), sign-in/sign-up 12 (`routes/api.php`). The nginx snippet `/etc/nginx/snippets/cf-resolve-ips.conf` (Cloudflare ranges for the real visitor address, shared by several vhosts) is static: `131.0.72.0/22` was added on 2026-10-03, compare it with https://www.cloudflare.com/ips-v4 and `/ips-v6` now and then (backup of the old file: `/root/cf-resolve-ips.conf.bak-2026-10-03`). Server side renders of the front end must call the API through localhost with the visitor's address in `X-Forwarded-For` (not through Cloudflare, where they all share the VPS address).

### Sessions
Browser sessions use `SESSION_DRIVER=database` with the table `luna_sessions` (config `SESSION_TABLE`; Winterchilla's own `sessions` table in the shared database has different columns, do not point Luna at it). The cookie driver put a ~800 byte cookie with a random name in the browser for every session started, and Celestia's parallel guest requests each start one (Sanctum treats `FRONTEND_URL` as stateful), which grew the Cookie header past nginx's 8k limit (Cloudflare 520); with the database driver the browser only ever holds `<cookie name>` and `XSRF-TOKEN`. Guest requests still create a row each, expired rows are swept by Laravel. `GET /users/sessions` lists the current user's sessions (`BrowserSession`: opaque `id` = sha256 of the session id, `device`, `ip`, `lastActiveAt`, `createdAt`, `current`) and `DELETE /users/sessions/{id}` ends one (the current one signs out through `POST /users/signout`); bearer tokens stay on `GET /users/tokens`. Changing the password also deletes the user's sessions.

### Model callbacks ported from Winterchilla
Winterchilla kept the tables consistent with ActiveRecord callbacks; Luna repeats the ones that touch data: `render_notes` (before every save of an appearance, `App\Utils\AppearanceNotes`, a `saving` event on `Appearance`: sanitized HTML, `>>123` Derpibooru links, `S1E3` episode links in the Friendship is Magic guide, `Movie#3`, `#123` appearance links, `\#`; the stored `notes_rend` is what both front ends show), `assign_order` (useful links via `eloquent-sortable`, color groups and colors in their controllers, appearances), `deleteVerifications` (`BlockedEmail::record` deletes the address's pending verifications), `make_related_entries` of point grants (`PcgPointGrant::record`) and the search index updates for pinning, deleting and saving (`AppearanceIndex`). Not repeated on purpose: removing cutie mark, sprite and rendered image files of `fs/` (Luna keeps its files in medialibrary, they are removed with the model) and Winterchilla's `CachedDeviation` rows (Luna caches deviations in Laravel's cache). Test: `ModelEventParityTest`.

### The OpenAPI document is committed
`docs/openapi/api-docs.json` is a copy of the generated document, kept in source control. `packages/api-types` builds the npm package `@went.tf/mlp-vectorclub-api-types` from it, and the `Publish API types` workflow publishes a new version whenever the file changes on `main` (trusted publishing, no token), which Celestia installs. The Node side uses pnpm (`pnpm-workspace.yaml` covers the root and `packages/api-types`, one `pnpm-lock.yaml`, `minimumReleaseAge` of 14 days, `packageManager` in the root `package.json`); the workflow installs with `pnpm install --frozen-lockfile`, builds with `pnpm build` and publishes with `npm publish` (the npm CLI does the OIDC/provenance part). `deploy.conf` runs `pnpm install --frozen-lockfile --prod --filter .` as the deploy user. `php artisan l5-swagger:generate` refreshes it by hand (the listener in `AppServiceProvider` calls `php artisan openapi:sync`, not on the server or in tests), `php artisan openapi:sync --check` fails when it is stale and `OpenApiDocumentTest` runs that check, so commit the file with every change to an attribute. After changing the API, push Luna first, wait for the publish, then raise the dependency in Celestia.

### The generated OpenAPI document is what Celestia builds against
Celestia generates its types from Luna's `/generated/api-docs.json`, not from Winterchilla's `api.json` (Winterchilla's contract is a design reference). The response schemas shared with the contract live in `app/OpenApi/ContractSchemas.php` (generated once from the contract, now maintained by hand). `python3 scripts/validate-responses.py [base url]` calls every GET operation against a running server (the contract server on :8766) and validates the response bodies against the schemas the document declares, it must report 0 problems; run it after changing a response shape or an annotation. `GenerateEnumDocblocks` (`php artisan generate-enum-docs`) writes the attribute files in `app/Helpers/types`.

### The color guide export no longer needs Winterchilla
`GET /color-guide/export` builds Winterchilla's `mlpvc-colorguide.json` live (Celestia serves it at `/dist/mlpvc-colorguide.json` through a rewrite). It follows the schema other tools read (`tests/fixtures/mlpvc-colorguide-schema.json`, a copy of Celestia's `public/dist` file, checked by `AdminTest::testExportFollowsTheSchemaOtherToolsRead` with justinrainbow/json-schema): tags carry `created_at`/`updated_at`; an empty `Appearances`, `Tags` or `ColorGroups` stays `[]` (the schema, version `?v1.2`, allows an empty list in place of the object).

### Generated images match Winterchilla
`App\Utils\AppearanceImages` (preview SVG, facing SVG, swatch JSON and GPL) and `App\Utils\PaletteImage` (palette PNG, GD + the two fonts in `resources/fonts`) are ports of Winterchilla's code, and `AppearanceImagesTest` / `PaletteImageTest` compare their output byte for byte with files that Winterchilla's own code produced (`tests/fixtures/winterchilla`, regenerated with `scripts/generate-winterchilla-*-goldens.php`, which need `../Winterchilla` with composer install and, for the palette and swatches, its `prod_copy` DB). Winterchilla's palette image used to miss the sprite because it looked for it at `<id>.png<id>.png`; that is fixed there (368625c4) and Luna draws the sprite next to the colors, the goldens are rendered by the fixed code.

### Scheduled commands
`gdpr:anonymize-logged-ips` (daily: `logs.ip` older than 3 months becomes `127.168.80.82`, failed auth attempts older than 3 months are deleted) and `gdpr:prune-email-verifications` (hourly: entries older than 24 hours), both registered in `App\Console\Kernel`. They only run while the server runs `php artisan schedule:run` every minute (cron).

### Nutshell names
The 2020 "nutshell names" mode stays (user decision, 2026-10-03). Winterchilla swapped labels while rendering HTML; in the API world every appearance object (`PreviewAppearance` and everything built on it) carries `nutshellNames`: the names it can be shown as, from `resources/data/nutshell_names.json` (a copy of Winterchilla's `config/nutshell_names.php`, 329 appearances; `App\Utils\NutshellNames`), always empty for personal guide appearances. Celestia applies it when the visitor's `cg_nutshell` preference is on: show a random one of the names, or the lowercased label when the list is empty; when the list is not empty the lowercased real label is also listed as an "also known as" name in the guide. `babelLabel` of Winterchilla's autocomplete is a UI detail, Luna does not return it.

### Test server fixtures for Winterchilla's browser UI tests (run against Celestia)
`scripts/serve-contract.sh` runs the test server with `TEST_FAKE_PROVIDERS=true`, `SESSION_DRIVER=database`, no `SESSION_DOMAIN` (host-only cookies) and mail logged to `storage/logs`. Routes that only exist with APP_ENV=testing: `POST /test/login/{id}` (bearer token for the contract suite), `GET /test/session-login/{id}?return=<path or front end URL>` (cookie session for a seeded user, redirects to `FRONTEND_URL` or to `return` when it stays on the front end's origin; Celestia rewrites its `/test-login/:id` to it), `PUT|DELETE /test/deviations/{id}` (body `{preview, fullsize?, title?, author?, type?, provider?}`: makes a deviation known like Winterchilla's Redis cache entries) and `PUT|DELETE /test/club-gallery/{id}` (club gallery acceptance, Winterchilla's marker files). With `TEST_FAKE_PROVIDERS` Luna asks neither DeviantArt nor image hosts: deviations come from those seeded entries (unknown ones are not found), images count as available PNGs and image URLs keep `http://`. `Kernel::$middlewarePriority` lists `EncryptCookies` before `StartSession`, without it a route in the `web` group sets an unencrypted session cookie.

### Running the contract suite against Luna
1. `scripts/load-contract-seed.sh` builds the `luna_contract` DB from `tests/fixtures/contract-seed.sql` (a copy of Winterchilla's `scripts/dump-contract-seed.sh` output, do not run that script against the shared test DB; pass another path to use a fresher dump) and attaches `tests/fixtures/cutiemark.svg` to the seeded cutie marks
2. `scripts/serve-contract.sh` serves Luna on :8766 (APP_ENV=testing, response cache off, restart after code changes)
3. In Winterchilla: `env CONTRACT_BASE_URL=http://127.0.0.1:8766 CONTRACT_API_PATH= CONTRACT_AUTH=bearer 'CONTRACT_LOGIN_URL=/test/login/{id}' vendor/bin/pest tests/Browser/Api/<File>.php`
- The whole suite passes against Luna (`--exclude-group=winterchilla-only`): the tests that assert Winterchilla's own API shape (UI fields such as `li`, `url`, `html`, routes Luna replaced like `/users/signout` and `/users/session/status`, `x-internal` endpoints, file checks, other status codes for the same case) carry that group. Run each file after a fresh `scripts/load-contract-seed.sh`: the tests change the data and later ones depend on it

Deploys reload every active php-fpm service (`deploy_restart` in `deploy.conf`), which clears the PHP stat cache and opcache of all workers; there is deliberately no API endpoint for it (Winterchilla's `DELETE /admin/stat-cache` is not ported, an endpoint can only reach one worker).

## Local setup

- URL: `https://api.mlpvector.lc` (nginx vhost is `/etc/nginx/conf.d/luna-lc.conf`, not in the repo; reuses the `mlpvector.lc` cert, which already lists `api.mlpvector.lc`). `CDN_URL=https://api.mlpvector.lc/cdn` serves `storage/app/public`
- php-fpm: shared pool socket `/run/php-fpm/php-fpm.sock`, no dedicated pool. `ext-exif` is enabled in `/etc/php/php.ini` (medialibrary needs it)
- OpenSearch: local service (`opensearch` package, `systemctl start opensearch`) on :9200 without the security plugin, single node. Not started by the tests (`AppearanceIndex` does nothing under APP_ENV=testing); to try the search for real run `APP_ENV=local DB_DATABASE=luna_contract php artisan tinker` and call `AppearanceIndex::rebuild()`
- Tests use the `luna_test` database (`DB_DATABASE` is forced in `phpunit.xml`); `tests/TestCase.php` refuses to run against any database not ending in `_test`. Build it with `createdb luna_test`, `psql -f setup/create_extensions.pg.sql`, then `DB_DATABASE=luna_test php artisan migrate`

## Gotchas

- Test models: `User::factory()->create()` leaves `role` null until refreshed, pass `['role' => Role::User]`
- `php artisan serve` keeps opcache between requests, use `scripts/serve-contract.sh` to restart after edits
- `Http::fake()` calls stack and the first match wins: reset the factory between fakes (see `tests/Feature/PostManagementTest.php`), and let `cloudflare.com` requests through

- `GET /about/sleep` sleeps for an hour outside production, never hit it
- `AboutController::serverInfo` reads `$_SERVER` directly, tests have to set the superglobals themselves
- `valorin/pwned-validator` calls its API through curl and caches per hash prefix, seed `Cache` (`pwned:<sha1 prefix>`) in tests (`tests/Concerns/FakesPwnedPasswords.php`)
- Opcache revalidates every 180s locally, after deleting `bootstrap/cache/packages.php` or changing providers, php-fpm can keep serving the old one for a few minutes
- `vendor/` must be owned by the deploy user, not root (a stray `sudo composer` breaks installs)
- Regenerate docs with `php artisan l5-swagger:generate`, Celestia builds its API types from `/generated/api-docs.json`

### Sprite SVG and the sprite color check
`sprite.svg` is no longer a port: Winterchilla drew one 1px stroke per horizontal run (and lost a pixel's color where two colors met). `App\Utils\SpriteImage::toSvg()` merges all pixels of a color (and opacity) into one even-odd path of outlines, pixel-exact (checked on all 104 production sprites, about 63% smaller), tested by redrawing the SVG (`AppearanceImagesTest`). `GET /appearances/{id}/sprite/colors` (`SpriteColorCheck`, brought back from Winterchilla's removed sprite color checker, without notifications) compares sprite and listed colors: unlisted colors are `near` a listed one (probably a mistake), a `blend` of two listed colors (mix, multiply, screen, both present in the sprite), or `unknown`; colors drawn only semi-transparent are not judged; under 5 pixels they are specks; palette colors with a parenthesised qualifier (`(Younger)`) are optional. The universal colors (appearance 0), the colors of every pinned appearance and the mannequin's four count as listed for every sprite and are named by where they are listed (`Pinned Pony | Eyes | Iris`), not as "(shared)". Calibrated on the production sprites: 88 of 104 come out clean.

### Double size sprites are pixel doubled
The `2x` sprite conversion (`size=600`, the file "Open image in new tab" shows, like Winterchilla's 600 px sprite) is an exact nearest neighbor doubling: medialibrary makes it with smooth interpolation, `App\Listeners\PixelateDoubleSizeSprite` (on `ConversionHasBeenCompletedEvent`) replaces the file with `App\Utils\PixelUpscale::double`. Sprites uploaded before that need `sudo -u www-data php artisan sprites:pixelate-2x` (safe to repeat, it redraws from the original; `--dry-run` reports files the user cannot write, it does not tell which are done). Do not use `media-library:regenerate` for it: it chmods every file it writes, which only the owner of a file may do, so as www-data it fails with "Disk named `public` cannot be accessed" on the files the deploy user owns. Tests: `PixelUpscaleTest`, `testSpriteUploadAndRemoval`.

### Websocket notifications (Muffins)
`App\Utils\WebsocketServer` links Luna to the websocket server that Winterchilla also used (the `Muffins` project). `WS_SERVER_HOST` (public address, shown as `wsServerHost`
of `GET /config`, null when unset), `WS_SERVER_URL` (how Luna reaches it from the server, e.g. `http://127.0.0.1:3672`) and `WS_SERVER_KEY` (the same secret as in Muffins'
`.env`) enable it; without them nothing changes (notifications are still polled by Celestia every minute). Browsers get a one time token from `POST /users/me/socket-token` (kept
two minutes in the cache, spent once); Muffins checks it with `POST /internal/websocket/validate` (bearer `WS_SERVER_KEY`, not in the OpenAPI document). `Notification::send` and
`POST /notifications/{id}/read` tell Muffins (`POST {WS_SERVER_URL}/notify`, 2 second timeout, a down server is only logged) to push the user's count, so open tabs fetch the list again.
Tests: `WebsocketServerTest`.

## API keys and the MCP server

- API keys are Sanctum tokens in `personal_access_tokens` with `is_api_key = true` (secret prefix `vck_`, hashed at rest, shown once). Sign-in tokens have `is_api_key = false`; `/users/tokens` only lists those. Managed through `ApiKeysController` / `App\Services\ApiKeys\ApiKeyService` (`/users/me/api-keys`), which need the password (`IdentityCheck`) and refuse key authentication.
- Scopes (`App\Enums\ApiKeyScope`) only narrow what the owner's role allows; `EnforceApiKeyScopes` (in the `api` group) applies them: authenticated GETs need `read:own`, other GETs `read`, writes the scope of their first path segment (`appearances`/`color-groups` → `appearances:write`, `posts` → `posts:write`, `users/*/preferences/*` → `user:write`). Account, session, token and e-mail routes are session-only. A new write area needs an entry in `WRITE_SCOPES`.
- The MCP endpoint is `POST /mcp` (`routes/ai.php`, `laravel/mcp`), key-only (`mcp.key`). Tools in `app/Mcp/Tools` extend `ApiTool`, are listed per key scope, and call the REST API in-process (`InternalApi`) so validation, permissions and privacy gating are not reimplemented. Add a tool to `VectorClubServer::$tools`.
- The key UI is `ApiKeysSection` on Celestia's account page.

## Read-only mode

`READ_ONLY=true` in `.env` turns the API into a viewer (`config('app.read_only')`): `ReadOnlyMode` (first in the `api` group) answers 503 `{message, readOnly: true}` (the flag tells it apart from the other 503s, deploying or maintenance) to everything that is not GET/HEAD/OPTIONS, signing in included, except `internal/websocket/validate`, which only reads. Sessions switch to the `array` driver (`config/session.php`), `App\Models\PersonalAccessToken` skips the `last_used_at` write, the scheduler only keeps `cloudflare:reload` and `horizon:snapshot`, and `GET /config` reports `readOnly` so Celestia shows its notice. With `DB_READ_USERNAME` / `DB_READ_PASSWORD` set, web requests (not artisan, so `migrate` on deploy keeps working) connect with that role, which should only have `SELECT`: a write that slips through then fails instead of changing data. Run `php artisan config:clear` (then `config:cache`) after changing any of these. Test: `tests/Feature/ReadOnlyModeTest.php`.
